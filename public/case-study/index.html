01 What was audited

A production app, publicly reachable, built with AI assistance and then deployed by hand. Exactly the shape of app this service exists for. The audit ran the six checks in order and stopped at each one to record evidence before moving on.

02 Findings

F-1High

Secrets are baked into the production image

Where

.dockerignore is 0 bytes, so COPY . . ships .env, .env.local and the whole .git directory into the image.

Evidence 
$ stat -c %s .dockerignore
0
$ docker exec clipper ls -la /app/.env /app/.env.local
-rw-rw-r-- 1 root root 1392 Sep 14 10:04 /app/.env
-rw-rw-r-- 1 root root  962 Sep 16 11:18 /app/.env.local
$ docker exec clipper sh -c '[ -d /app/.git ] && find /app/.git -type f | wc -l'
28
Impact

AUTH_SECRET lives inside the image layers. Anyone who can read the image — a registry, a host, a backup, a docker save — can forge a session cookie for any account, and gets the full git history with it.

Fix

A real .dockerignore, then rebuild and rotate AUTH_SECRET — the old one has to be treated as burned.

Estimate

1 hour

F-2High

Uploads are written to a path that is not mounted, so every deploy deletes them

Where

The storage root is ./storage whenever CONTENT_STORAGE_PATH is unset. The container's only mount is /app/data.

Evidence 
$ docker exec clipper printenv CONTENT_STORAGE_PATH
(empty)
$ docker inspect clipper --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
/home/cosmic/app/clipper/data -> /app/data
$ docker exec clipper sh -c 'find /app/storage -type f | wc -l'
0
Impact

The database survives — it points at a mounted path. The files do not. Every uploaded video, thumbnail and avatar lands in the container's writable layer and is destroyed on the next deploy, leaving database rows pointing at files nobody can open. It is latent only because nothing has been uploaded yet.

Fix

Set CONTENT_STORAGE_PATH to a mounted directory.

Estimate

1 hour

F-3High

The app thinks it is running on http://localhost:3000

Where

Container env NEXT_PUBLIC_BASE_URL, consumed by the social OAuth config and the OAuth callback route.

Evidence 
$ docker exec clipper printenv NEXT_PUBLIC_BASE_URL
http://localhost:3000

$ curl -sI https://clipper.soyuz.my.id/api/content | grep -i location
location: /login?callbackUrl=https%3A%2F%2Flocalhost%3A3000%2Fapi%2Fcontent

$ curl -s -o /dev/null -D - -H 'Host: clipper.soyuz.my.id' \
    http://127.0.0.1:3000/api/content | grep -i location
location: /login?callbackUrl=http%3A%2F%2Flocalhost%3A3000%2Fapi%2Fcontent

$ curl -s -o /dev/null -D - -X POST \
    https://clipper.soyuz.my.id/api/auth/callback/credentials ... | grep -i location
location: https://localhost:3000/login?error=CredentialsSignin&code=credentials
Impact

The origin stays localhost:3000 even when the request carries the real host header, so the value is coming from the environment and not from the request. Two things break: a mistyped password sends the browser to an unreachable host instead of saying "Invalid email or password", and the redirect_uri handed to the social platforms points at a machine that only exists on the developer's laptop — so connecting an account can never complete.

Fix

Set the base URL to the real domain and rebuild.

Estimate

1 hour

F-4Medium

The env schema guards 2 of the 12 variables the code reads

Where

The startup validation schema checks DATABASE_URL and AUTH_SECRET and nothing else.

Evidence 
code reads:   AI_PROVIDER AI_GATEWAY_MODEL AI_GATEWAY_BASE_URL AI_GATEWAY_API_KEY
              DATABASE_URL NODE_ENV NEXT_PUBLIC_BASE_URL CONTENT_STORAGE_PATH
              CONTENT_MAX_UPLOAD_MB (+6 OAuth vars)
in container: AUTH_SECRET AUTH_TRUST_HOST DATABASE_URL NEXT_PUBLIC_BASE_URL
              NODE_ENV (+ base image vars)
Impact

This is why F-2 and F-3 shipped. A missing or dev-default integration variable raises nothing at boot. The app starts, looks healthy, and fails only when a user walks into that path.

Fix

Validate every variable the code reads and fail fast at startup.

Estimate

2 hours

F-5Medium

Production runs the AI features on mock data

Where

The AI config defaults to the mock provider when no provider is selected.

Evidence 
$ docker exec clipper printenv AI_PROVIDER
(empty)  → getAIConfig() returns provider "mock"
Impact

The mock provider describes itself honestly in its own source: "deterministic, schema-valid mock data with just enough variance to feel alive." Ideas, hooks, scripts, viral scores and analytics patterns are generated locally and returned through the same response shape as a real model, so nothing in the interface says the output is invented. Reasonable for a demo, misleading in production.

Fix

Point it at a real gateway, or label mock mode in the UI.

Estimate

1 hour

F-6Low

A developer machine's address left in the production config

Where

The Next.js config whitelists one hard-coded personal IP as an allowed dev origin.

Impact

Nothing breaks today. It is a personal address shipped in production config, and it widens what the dev-origin check accepts.

Fix

Remove it, or gate it behind a production check.

Estimate

15 minutes

03 What passed

A report that only lists problems is not a measurement. These were checked and came back clean — and the client is told so.

  • No secret reaches the browser. All 9 JavaScript chunks served by the live site were downloaded and scanned for key patterns. The 9 raw hits were all a CSS utility class (mask-image-linear-from-pos) coincidentally matching a key prefix — zero real matches. Source maps are not published.
  • Every route is gated on the server. Auth middleware covers everything except the auth endpoints, and all 10 API paths probed without a session returned a redirect to the login page. Server actions re-check the session too, so there is no client-only guard anywhere.
  • Path traversal is refused. The storage layer rejects any key that escapes its root.
  • The integrations do not fail silently. No empty catch blocks, and all 7 outbound HTTP calls check the response status and throw with it.
  • Credentials stay out of git. The env files are untracked and ignored. F-1 is about the image, not the repository.
  • The alarming cache header is harmless. The login page ships a one-year shared-cache header, but Cloudflare reports the response as DYNAMIC on repeated requests — it is never cached, so no stale token can be served.

Recommendation. Fix F-1, F-2 and F-3 first — three hours, and they are one ignore file, two environment variables and a rebuild. Nothing here needs a rewrite, and none of it is a code-quality problem: the code is careful, the deployment drifted away from it. Then F-4, so the same class of drift fails loudly instead of silently. F-5 needs a product decision before it needs code. F-6 is cleanup.

What was not checked. Database contents beyond row counts. Penetration testing of the AI gateway. Database indexing, and the business logic inside the 11 API routes. Load testing. Mobile and accessibility review of the dashboard UI. The OAuth flows could not be exercised end to end, because no provider credentials are configured — which is itself part of F-3 and F-4.
